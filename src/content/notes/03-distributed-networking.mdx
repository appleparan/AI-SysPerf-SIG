## NCCL Internals

### Q1. Communicator 초기화 시점과 collective 호출 시점에 정해지는 것

> 책에서는 다음과 같은 문장이 있다.
>
> "By default, NCCL's communicator initialization automatically inspects the message size, interconnect topology, and GPU generation to automatically pick the fastest algorithm and protocol combination for each collective and topology."
>
> 하지만 communicator초기화과정에서 알 수 없는 정보들도 있을텐데 Init시점에서 결정되는것과 실제 collective 호출시점에서 결정되는것들은 정확히 어떤건지 궁금합니다.

**이번 모임에서는 답을 정리하지 못했습니다.** 발표자는 질문에 답하려면 NCCL 내부 동작을 더 알아야 한다고 했습니다. 열린 질문으로 남깁니다.

### Q2. 채널 수와 버퍼 크기는 trade-off인가

> NCCL은 all-reduce, all-gather 같은 collective를 토폴로지에 맞게 자동으로 최적화해 대역폭을 최대한 활용하게 해주는 라이브러리입니다.
>
> 이 과정에서 채널과 버퍼라는 개념이 등장하는데, 채널은 일종의 차선, 버퍼는 차선당 한 번에 실어나르는 양으로 이해했습니다. 그렇다면 채널 수와 버퍼 크기는 서로 trade-off 관계인가요? 아니면 각각 다른 비용을 치르면서 대역폭 활용을 높이는 요소인가요?

**발표자는 trade-off보다 한정된 자원을 나눠 쓰는 문제로 이해했습니다.** 채널과 버퍼 모두 GPU 자원을 쓰므로, 정해진 자원 안에서 어떻게 배분하느냐의 문제라는 해석입니다. 더 깊은 근거는 정리하지 못했습니다.

### Q3. vLLM에서 NCCL_CUMEM_HOST_ENABLE=0이 필요한 이유

> vllm을 쓰다보면 NCCL_CUMEM_HOST_ENABLE 를 디폴트 값이 아닌 0으로 잡아줘야 할 때가 많았습니다. 이 환경변수에 대해 알고 계시는 부분이 있으면 설명 부탁드리겠습니다.

**모임에서는 답을 찾지 못했고, NVIDIA 문서로 보충합니다.** 이 변수는 NCCL이 프로세스 간 공유 메모리로 `/dev/shm` 대신 cuMem host allocation을 쓸지 정합니다.

**NCCL은 같은 노드의 프로세스끼리 host 메모리를 공유합니다.** 여기서 host 메모리는 CPU 쪽 시스템 DRAM입니다. vLLM에서 Tensor Parallel을 쓰면 GPU마다 프로세스가 따로 뜨고, NCCL은 이 프로세스들 사이의 버퍼를 DRAM에 둡니다. 이 공유 메모리를 만드는 방법이 두 가지입니다.

- **`/dev/shm` 방식**: 프로세스 A가 `/dev/shm`에 파일을 만들고, 프로세스 B가 같은 경로를 엽니다. Linux 파일 시스템이 메모리를 관리합니다.
- **cuMem host 방식**: 프로세스 A가 CUDA Driver에 DRAM 할당을 요청하고, 그 메모리를 가리키는 핸들(번호표)을 받습니다. A는 이 핸들을 파일 디스크립터로 바꿔 Unix socket으로 B에 넘기고, B는 핸들로 같은 DRAM을 매핑합니다. CUDA Driver가 메모리를 pinned 상태로, 특정 NUMA 노드에 잡습니다.

<ThemeImage lightSrc="/images/notes/03/cumem-host-light.svg" darkSrc="/images/notes/03/cumem-host-dark.svg" alt="A /dev/shm 방식: Process A와 B가 같은 /dev/shm 파일 경로를 열어 Host DRAM 공유 버퍼를 함께 본다. B cuMem host 방식: Process A가 CUDA Driver에 할당을 요청하고, 받은 핸들(fd)을 Unix socket으로 Process B에 넘기며, B가 핸들로 pinned · NUMA 노드 지정 Host DRAM을 매핑한다" class="mx-auto w-full max-w-[720px]" />

결과는 같습니다. 두 프로세스가 같은 DRAM 페이지를 공유합니다. 차이는 관리 주체이고, cuMem 방식은 NUMA 지원이 막힌 환경에서 실패할 수 있습니다. `NCCL_CUMEM_HOST_ENABLE=0`은 cuMem 방식을 끄고 `/dev/shm` 방식으로 돌아가는 스위치입니다.

| 항목 | 내용 |
| --- | --- |
| 도입 | NCCL 2.23 |
| 기본값 | NCCL 2.24부터, CUDA Driver 12.6 이상과 CUDA Runtime 12.2 이상이면 켜짐 |
| 실패 조건 | NUMA 지원이 올바르게 동작해야 함. Docker는 기본적으로 NUMA 지원을 끔. Driver 13.0 미만에서 CUDA P2P 연결이 없으면 할당이 실패할 수 있음. CUDA Forward Compatibility 환경에서는 Driver 버전을 잘못 판단할 수 있음 |
| 대응 | NCCL 2.26.5부터는 동작 여부를 확인하고 `/dev/shm`으로 자동 fallback. 그 이전 버전은 `NCCL_CUMEM_HOST_ENABLE=0`으로 끔. Docker는 `--cap-add SYS_NICE`로 NUMA 지원을 켬 |

vLLM을 컨테이너에서 돌릴 때 0으로 설정해야 했던 것은 위의 NUMA 조건 때문일 가능성이 있습니다. 직접 확인하지는 않았습니다. 문서는 가능하면 끄지 말고 시스템을 맞추라고 권합니다. cuMem host allocation이 communicator abort 상황에서 더 안정적이기 때문입니다.

출처: [NCCL User Guide, cuMem host allocations](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/runtime_and_mpi_issues.html#cumem-host-allocations)

## Compute–Communication Overlap

### Q4. 연산과 통신을 겹치기 어려운 워크로드

> 챕터4는 멀티 노드(GPU)에서 최적화 방식을 말하고 있으며 제가 볼때는 GPU자체 성능 보다는 GPU 간의 통신의 최적화를 의미하는 것 같습니다.
>
> 실제 연산과정과 데이터 통신 과정이 동시에 이루어 질러면 어떤 형태로 해야 하는지 궁금합니다. 예를 들어서 Convolution 연산 집중된 작업에서는 잘 이루어 질거 같고 LLM, RNN 같은 Recurrent 작업은 불리할거 같습니다

**판단 기준은 연산이 시작되기 전에 그 연산에 필요한 데이터가 모두 도착했는가입니다.** 다음 연산의 입력이 앞 연산의 결과에 묶여 있으면 통신을 미리 당겨 올 수 없습니다.

| 워크로드 | 겹치기 | 이유 |
| --- | --- | --- |
| CNN, LLM 학습 | 가능 | 레이어별 gradient 통신을 다음 레이어의 backward 연산과 겹칠 수 있음 |
| LLM Prefill | 가능성 있음 | 입력 토큰 전체를 한 번에 처리하므로 연산량이 큼 |
| LLM Decode, RNN | 어려움 | 토큰이나 타임스텝마다 앞 결과가 있어야 다음 연산을 시작함 |

## KV Cache Offloading

### Q5. KV Cache를 SSD에서 복원할 것인가, 다시 계산할 것인가

> NIXL을 이용하면 KV 캐시를 NVMe SSD로 오프로딩할 수 있다고 이해했습니다. 하지만 저장한 캐시를 재사용하려면 GPU로 다시 가져와야 하므로, PCIe 기반 환경에서는 추가적인 전송 비용이 발생할 것 같습니다.
>
> 캐시를 SSD에 보관했다가 복원하는 방식과, 캐시를 버리고 필요할 때 재계산하는 방식은 어떤 기준으로 선택하는지와 캐시 크기, 실제 전송 대역폭, 재계산 시간, 계산과 전송의 중첩 가능성을 고려했을 때 두 방식의 손익분기점을 어떻게 판단할 수 있을지 궁금합니다.

**손익분기점 자체는 단순합니다.** 복원 때문에 실제로 기다리는 시간이 재계산 때문에 기다리는 시간보다 짧으면 복원합니다.

$$
T_{\text{복원으로 인한 실제 대기}} < T_{\text{재계산으로 인한 실제 대기}}
$$

**발표자는 요청 한 건이 아니라 여러 요청이 동시에 있는 상황에서 따져야 한다고 봤습니다.** 그래서 통신 비용을 감수하고라도 저장할 가치가 있는 데이터, 즉 버리기 아까운 캐시가 무엇인지부터 정리했습니다.

| 상황 | SSD에 보관하는 이유 |
| --- | --- |
| 긴 대화 세션이 많음 | 사용자가 다음 질문을 할 때까지 모든 대화의 KV를 VRAM·RAM에 유지하기 어려움 |
| 긴 문서를 두고 반복 질문 | 동일한 입력 prefix를 다시 처리하는 Prefill 비용을 줄이고 싶음 |
| 에이전트가 도구 실행 등을 기다림 | 잠시 사용하지 않는 캐시를 내려 다른 요청에 GPU 메모리를 제공 |
| 재사용할 캐시 전체가 RAM보다 큼 | 자주 쓰는 캐시는 RAM에, 덜 자주 쓰는 캐시는 SSD에 보관 |

#### 토론: 오프로딩은 KV Cache가 늘 모자라서 쓴다

진행자는 오프로딩을 쓰는 가장 큰 이유가 GPU 메모리의 KV Cache 부족이라고 보충했습니다. B300급 최신 GPU로 큰 모델을 서빙해도, 긴 컨텍스트에서 동시에 받을 수 있는 사용자는 수십 명 수준에 그칩니다. 가중치를 올리고 남은 메모리로는 KV Cache가 생각보다 빠듯합니다.

진행자는 DeepSeek 사례도 들었습니다.

- DeepSeek V4부터는 KV Cache를 스토리지에 캐싱합니다. 이를 위해 모델 아키텍처 단계에서 KV Cache를 극단적으로 압축하면서도 성능을 유지했다고 설명했습니다.
- DeepSeek은 파일 시스템([3FS](https://github.com/deepseek-ai/3FS))까지 직접 만들었기 때문에 이 방식이 더 효율적입니다.

결론은 KV Cache 오프로딩을 제대로 쓰려면 모델만이 아니라 KV Cache에 맞는 스토리지 인프라가 함께 필요하다는 것입니다.

### Q6. NCCL이 P2P를 지원하는데 NIXL이 왜 필요한가

> NCCL도 P2P를 지원하는데 NIXL이 왜 필요할까요? NCCL도 send/recv와 GPU Direct RDMA를 지원하지만 NIXL이 KV Cache 전송에서 제공하는 실질적인 이득이 무엇일지, 동일한 하드웨어와 RDMA를 사용할 때 어떤 구조적 차이가 성능 차이로 나타날지 궁금합니다.

**책 기준으로 두 라이브러리는 다루는 대상이 다릅니다.**

| NCCL | NIXL |
| --- | --- |
| GPU 사이의 통신, 특히 collective | CPU 메모리와 저장장치까지 포함해, 데이터가 있는 위치와 옮길 위치를 지정해 전송 |

발표자는 처음에 이 구분으로 이해했지만, 찾아보니 NCCL로도 비슷한 전송이 가능해 보였다고 했습니다. 그래서 GPU 밖으로 데이터를 옮기는 경우에 NIXL이 편의를 제공하는 정도로 본다고 정리했습니다. 같은 하드웨어와 RDMA에서 구조적 성능 차이가 어디서 나는지는 다루지 못했습니다.

## Disaggregated Inference

### Q7. 분산 추론은 언제 이득인가

> 분산형 추론은 어느 시점에서 이득인가요? KV Cache 전송 비용으로 손익 분기점을 계산해볼 수 있을까요?

**분리로 줄어드는 처리·대기 시간이 KV 전송 시간과 추가 제어 비용보다 크면 이득입니다.**

$$
\text{분리로 줄어드는 처리·대기 시간} > \text{KV 전송 시간} + \text{추가 제어 비용}
$$

**발표자는 답을 준비하면서 오히려 언제 쓰는지 의문이 생겼다고 했습니다.** GPU 2장에 모델을 올리는 경우를 비교했습니다.

- 일반적인 모델 병렬화는 가중치를 나눠 올리고, GPU 사이에 중간 결과를 주고받습니다.
- 분산 추론(PD Disaggregation)은 가중치를 나누지 않습니다. 양쪽 GPU에 가중치를 모두 올리고, 한쪽은 Prefill만, 다른 쪽은 Decode만 처리합니다.

가중치가 양쪽 메모리를 모두 차지하므로 이득이 많이 사라지지 않느냐는 것이 발표자의 의문이었습니다.

#### 현장 코멘트: 이기종 GPU에 Prefill과 Decode를 나누면?

한 참가자는 기종이 섞인 GPU 서버를 운영해 본 경험을 들려줬습니다. 연산이 많은 Prefill은 큰 GPU에, Decode는 저렴한 GPU에 나누면 이득일 것 같아 관심을 가졌다고 합니다. 그러나 가중치는 양쪽에 모두 올려야 합니다. 또 NVLink가 있는 GPU와 없는 GPU의 통신 속도 차이가 체감상 컸습니다. 그래서 NVLink 없이 KV를 넘기면 사용자가 첫 토큰을 받기까지 더 오래 걸릴 것 같다고 했습니다.

#### 진행자 정리: 간섭이 심하거나 이기종 클러스터일 때 쓴다

PD Disaggregation이 유리한 경우는 두 가지입니다.

1. **Prefill이 Decode를 심하게 간섭할 때**: 한 GPU에서 둘을 섞어 처리하면 긴 Prefill이 Decode 토큰 생성을 밀어냅니다. 나누면 이 간섭이 사라집니다.
2. **GPU가 이기종 클러스터로 구성되어 있을 때**: 연산이 많은 Prefill과 메모리 대역폭이 중요한 Decode를 각자 맞는 GPU에 배치할 수 있습니다.

다만 InfiniBand나 NVLink 같은 고속 연결이 없으면 KV 전송 비용이 분리로 얻는 이득보다 클 수 있습니다. 위의 손익분기 식을 실제 환경의 대역폭으로 따져 보고 상황에 맞게 선택해야 합니다.
